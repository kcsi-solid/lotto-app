# 로또 번호 분석기

동행복권 **1회 ~ 최신 회차** 당첨 데이터를 **시계열 순서**로 분석해 번호를 생성하는 웹앱입니다.
설치 없이 브라우저에서 돌아가고, PWA라서 핸드폰 홈 화면에 앱처럼 설치할 수 있으며, 오프라인에서도 동작합니다.

---

## 빠르게 실행하기

```bash
cd C:\Users\kcseo\lotto-app
python -m http.server 8000
```

브라우저에서 <http://localhost:8000> 을 엽니다.

> `file://` 로 직접 열면 동작하지 않습니다. ES 모듈과 `fetch`가 `http://` 를 요구합니다.

### 테스트

```bash
npm install      # jsdom (테스트에만 필요)
npm test         # 엔진 26개 + UI 65개 검사
```

### 데이터 갱신

```bash
python tools/fetch_draws.py              # 전체 갱신
python tools/fetch_draws.py --since 1230 # 최근 회차만
```

앱 안에서는 **설정 → 데이터 갱신 → 최신 회차 가져오기** 로도 됩니다.
새 회차가 없으면 파일을 아예 건드리지 않으므로, 반복 실행해도 안전합니다.

### 백테스트

```bash
npm run backtest                                  # 기본 (200회차 × 5게임)
npm run backtest -- --holdout 600 --games 20
```

## ⚠️ 먼저 알아야 할 두 가지 사실

### 1. "실제 나온 순서" 데이터는 존재하지 않습니다

요구사항은 "번호의 나열이 아닌 **실제 나온 순서**로 로직을 계산"하는 것이었습니다.
그런데 1241개 회차를 전부 검증한 결과, **모든 회차의 6개 번호가 100% 오름차순으로만 저장**되어 있습니다.
동행복권은 공식 API로든 웹페이지로든 **물리적인 볼 추첨 순서를 공개하지 않습니다.**

그래서 "순서"를 다음 두 가지로 해석해 구현했습니다. 둘 다 진짜 순서 정보입니다.

| 해석 | 내용 | 쓰는 곳 |
|---|---|---|
| **회차 간 시계열 순서** | 1회 → 2회 → … → 1241회라는 실제 시간 흐름 | 마르코프 전이 (핵심) |
| **회차 내 오름차순 위치** | 1번째 자리 ~ 6번째 자리의 값 분포 | 위치 분포 지표 |

만약 볼 추첨 순서 데이터를 따로 확보하신다면, `data/draws.json` 의 `n1~n6` 을
오름차순이 아닌 실제 추첨 순서로 넣으면 위치 분포 지표가 자동으로 진짜 추첨 순서 분석이 됩니다.
엔진 코드는 고칠 필요가 없습니다.

### 2. 백테스트 결과: 무작위와 통계적으로 차이가 없습니다

이건 추측이 아니라 측정한 값입니다. `npm run backtest` 로 직접 재현할 수 있습니다.

**워크포워드 검증** — 회차 `t`를 맞힐 때 `draws[0 .. t-1]` 만 엔진에 넘깁니다.
`t`회차가 통계에 섞이면(look-ahead) 결과가 통째로 무의미해지므로 코드에 단언문으로 막아뒀습니다.

`--holdout 600 --games 20` (600회차 × 20게임 = 12,000게임) 실행 결과:

| 방법 | 게임당 평균 적중 |
|---|---|
| 이론적 기대값 (완전 무작위) | 0.8000 |
| **엔진** | **0.7801** |
| 무작위 | 0.8027 |
| 필터만 (점수 없이 분포 필터만) | 0.7980 |

유의성 검정 (회차 단위 대응표본, n=600):

| 비교 | 차이 | 표준오차 | t | 판정 |
|---|---|---|---|---|
| 엔진 − 무작위 | −0.0226 | 0.0165 | −1.37 | 차이 없음 |
| 엔진 − 필터만 | −0.0179 | 0.0157 | −1.14 | 차이 없음 |
| 필터만 − 무작위 | −0.0047 | 0.0099 | −0.47 | 차이 없음 |

12,000게임 전체에서 5개 이상 적중은 **0회**, 4개 적중은 엔진 13회 / 무작위 18회였습니다.

> **왜 회차 단위로 묶어 검정하는가**: 같은 회차에서 뽑은 20게임은 같은 통계에서 나와
> 서로 독립이 아닙니다. 게임 하나하나를 표본으로 세면 표본 수가 부풀려져
> 실제보다 유의해 보입니다. 회차끼리는 독립 시행이므로 회차별 평균을 표본 하나로 묶습니다.

직전 회차 번호가 다음 회차에 다시 등장하는 개수도 같은 이야기를 합니다.

```
실측 평균     0.827개
무작위 기대값 0.800개
```

**이 프로그램은 당첨 확률을 높이지 않습니다.**
목적은 *근거를 설명할 수 있고, 같은 시드로 재현 가능한 번호 선택*입니다.
1등 확률은 어떤 방법을 쓰든 8,145,060분의 1로 같습니다.

## 계산 로직

번호 1~45 각각에 대해 4개 지표를 계산하고, 각각을 **z-점수로 표준화**한 뒤 가중합합니다.

### 지표 1 — 시간 가중 출현 빈도 `freq`

회차마다 가중치를 다르게 줍니다.

```
w(t) = 0.5 ^ (경과회차 / 반감기)
```

반감기 기본값은 260회차(약 5년)입니다. 5년 전 회차의 영향력이 지금의 절반이라는 뜻입니다.
단순 누적 빈도와 달리 최근 경향을 더 크게 반영합니다. 반감기는 설정에서 20~1200 사이로 조절합니다.

### 지표 2 — 회차 간 마르코프 전이 `markov` ← 순서 로직의 핵심

시간 순서를 따라 45×45 전이확률 행렬을 만듭니다.

```
P(j가 t+1회에 등장 | i가 t회에 등장)
```

직전 회차에 나온 6개 번호에서 각 후보 `j`로 가는 전이확률의 **평균**이 그 번호의 점수입니다.

```
markov(j) = (1/6) × Σ  P(i → j)
                  i ∈ 직전회차
```

행렬의 대각선(`i = j`)은 같은 번호가 연속 회차에 다시 나오는 비율을 그대로 담습니다.
**단순 빈도 집계로는 절대 얻을 수 없는, 순서에서만 나오는 정보입니다.**
전이 횟수에도 지표 1과 같은 시간 가중치를 적용합니다.

### 지표 3 — 간격 분석 `gap`

번호마다 등장 간격의 평균을 구한 뒤:

```
hazard(n) = 현재 미등장 회차 수 / 그 번호의 평균 간격
```

핵심은 "전체 평균보다 오래 안 나온 번호"가 아니라 **"자기 리듬보다 밀린 번호"** 를 찾는 것입니다.
평균 간격이 6회인 번호가 9회 쉰 것과, 평균 간격이 9회인 번호가 9회 쉰 것은 의미가 다릅니다.

### 지표 4 — 오름차순 위치 분포 `position`

당첨번호를 작은 수부터 늘어놓으면 1번째 자리에는 낮은 수, 6번째 자리에는 높은 수가 오는
실제 편향이 있습니다. 6개 자리 중 그 번호가 가장 잘 맞는 자리의 확률을 씁니다.

```
position(n) = max   P(n이 p번째 자리)
             p=1..6
```

### 합산

네 지표는 단위가 서로 달라 그대로 더할 수 없습니다(빈도는 0~0.15, hazard는 0~5 범위).
각각 `z = (값 − 평균) / 표준편차` 로 표준화한 뒤 가중합합니다.

```
score(n) = 0.30·z_freq + 0.30·z_markov + 0.25·z_gap + 0.15·z_position
```

가중치는 설정 화면에서 실시간으로 조절할 수 있고, 바꾸면 분석 차트가 즉시 갱신됩니다.

### 조합 선택

- **1게임째**: 점수 상위 6개를 결정론적으로 선택합니다. 필터에 걸리면 차순위와 교체합니다.
- **2게임째부터**: `softmax(score / temperature)` 가중치로 중복 없이 표본추출합니다.
  점수 분포는 따르되 게임마다 다른 조합이 나옵니다.
  `temperature`가 낮을수록 고득점 번호에 집중되고, 높을수록 고르게 퍼집니다.
- **시드**: 같은 시드를 넣으면 언제나 같은 번호가 나옵니다. 비워두면 매번 새로 뽑습니다.

#### 조합 응집도 `scoreSetCohesion()` — 현재 무보정

매 게임마다 후보 조합을 8개 뽑아 이 함수의 점수가 가장 높은 것을 채택하는 구조가
`generateGames()` 안에 배선돼 있습니다. 번호별 점수는 45개를 따로 평가하므로
"이 6개가 서로 어울리는가"를 원리적으로 볼 수 없어서 만든 확장 지점입니다.

**현재는 `0`을 반환해 보정하지 않습니다.** 모든 후보가 동점이 되어 맨 처음 후보가 채택됩니다.

한때 여기서 *15개 쌍의 lift 평균*을 점수로 썼습니다. 조합에서만 나오는 신호라 근거는
그럴듯했지만, 백테스트에서 효과가 없어 걷어냈습니다.

| | 게임당 평균 적중 | t (엔진−무작위) |
|---|---|---|
| **무보정 (현재)** | **0.7801** | **−1.37** |
| 쌍 연관성 적용 | 0.7757 | −1.64 |

함수는 의도대로 동작했습니다. 그런데 예측력은 나아지지 않았고 오히려 미세하게 낮아졌습니다.
한 쌍의 기대 동시출현이 22회뿐이라 관측된 lift 편차는 대부분 표본 오차이고,
그걸 좇는 것은 **과거의 우연을 미래에 투영하는 일**이기 때문입니다.

다른 조합 수준 지표를 시험해 보고 싶다면 이 함수에 넣고 `npm run backtest` 로
효과를 측정하면 됩니다. 배선은 그대로 살아 있습니다.

> **쌍 연관성 `stats.lift` 를 쓸 때의 주의** — 기대 동시출현을 `p_i × p_j × T`로 잡으면
> 틀립니다. 그건 독립 추출 가정인데 로또는 45개에서 6개를 **비복원**으로 뽑습니다.
> 올바른 값은 `(6/45) × (5/44)`이고, 보정을 빼면 모든 lift가
> `(5/44)/(6/45) = 0.8523`배로 눌려 "1.0 = 우연" 기준선이 깨집니다.
> 초기 구현에 이 버그가 있었고 자체 검사의 음성 대조가 잡았습니다.
> 보정은 `buildStats()` 안에 남아 있으며, 검사가 계속 지킵니다.

### 역사적 분포 필터

1~1241회 실측 분포에서 뽑은 임계값입니다. **"불가능"이 아니라 "역사적으로 드물다"** 는 뜻입니다.

| 조건 | 임계값 | 실측 근거 |
|---|---|---|
| 6개 합계 | 100 ~ 177 | p10=98, p90=177 |
| 홀수 개수 | 2 ~ 4개 | 전체의 82% |
| 연속 번호 | 최대 2개 | 전체의 95% |
| 구간 분산 | 5개 구간 중 3개 이상 | 전체의 97% |
| 과거 1등 조합 | 완전히 같은 조합 제외 | — |

필터는 체크박스로 끌 수 있습니다. 필터가 너무 빡빡해 요청한 게임 수를 못 채우면
자동으로 필터를 풀어서라도 **요청한 게임 수는 반드시 채웁니다.**

### 결과 표시

**5게임 단위**로 조를 나눠 보여줍니다. 12게임이면 `5 + 5 + 2` 로 3개 조가 됩니다.
번호 공은 동행복권과 같은 색 규칙(1-10 노랑, 11-20 파랑, 21-30 빨강, 31-40 회색, 41-45 초록)을 씁니다.

**조합 확률** — 각 게임 아래에 `이 조합이 나올 확률`이 %로 표시됩니다.
계산은 세 단계이고, 화면에도 이 근거가 그대로 나옵니다.

```
1. 번호 점수  = 빈도×0.30 + 마르코프×0.30 + 간격×0.25 + 위치×0.15   (각각 z-표준화)
2. 번호 확률  = softmax(점수 ÷ temperature) × 6
               45개를 더하면 6.0. 45개를 모두 똑같이 본다면 각각 13.3%
3. 조합 확률  = 6개 번호 확률을 모두 곱함
               45개를 모두 똑같이 본다면 (13.3%)⁶ = 0.00056%
```

가중치와 `temperature`는 **설정의 현재 값을 그대로 읽어** 표시하므로, 슬라이더를 움직이면
화면의 식도 함께 바뀝니다. 실제 출력 예:

| 조합 | 이 조합이 나올 확률 |
|---|---|
| 3 · 6 · 13 · 27 · 38 · 45 | 0.9629% |
| 3 · 6 · 13 · 35 · 38 · 45 | 0.2127% |
| 3 · 12 · 16 · 27 · 33 · 37 | 0.0492% |
| 3 · 13 · 16 · 17 · 38 · 40 | 0.0102% |
| 1 · 3 · 9 · 27 · 30 · 38 | 0.006295% |

기준선은 `0.00056%`입니다. 45개 번호를 모두 똑같이 본다면 나오는 값이고,
그보다 높으면 이 모델이 더 유망하게 본다는 뜻입니다.

> **두 가지 한계를 화면에도 적어 뒀습니다.**
> 1. 이 확률은 **이 모델의 추정**입니다. 곱셈은 6번의 추출이 서로 독립이라고 가정한 값이라
>    엄밀한 결합확률도 아닙니다(실제 로또는 비복원 추출).
> 2. **실제 1등 당첨 확률은 어떤 조합을 골라도 `1/8,145,060 = 0.0000123%`로 같습니다.**

체크박스로 끌 수 있으며, 껐다 켜도 **번호를 다시 뽑지 않고 표시만 바뀝니다.**
합계·홀짝 표시는 화면에서 뺐습니다(필터 조건으로는 계속 쓰입니다).

**초기화 버튼** — 생성된 결과와 시드 입력을 지우고 처음 상태로 되돌립니다.
설정·가중치·데이터는 건드리지 않습니다. 설정을 되돌리려면 설정 탭의 `설정 초기화` 를 쓰세요.

## 데이터 획득

동행복권(`dhlottery.co.kr`)의 공개 JSON 엔드포인트는 현재 **봇 차단(NetFUNNEL 대기열)** 이 걸려 있어
curl·서버·다른 사이트에서 호출하면 전부 대기열 페이지로 되돌아갑니다.
검증 결과 User-Agent, 세션 쿠키, TLS 스택을 바꿔도 마찬가지였습니다.
그래서 획득 경로를 세 갈래로 분리했습니다.

| 경로 | 파일 | 특징 |
|---|---|---|
| **① 번들 데이터** | `data/draws.json` | 앱에 동봉. 오프라인에서도 즉시 동작. **기본값** |
| **② 원격 증분 갱신** | `js/source.js` | 설정한 엔드포인트에서 최신 회차만 추가 |
| **③ 브라우저 직접 수집** | `tools/collect-in-browser.js` | 동행복권 공식 데이터를 확실하게 받는 방법 |

### ③ 동행복권에서 직접 수집하기

정상 브라우저로 사이트에 들어가 있으면 **같은 출처(same-origin)** 요청이라 CORS도 봇 차단도 걸리지 않습니다.

## API 키와 개인정보

기본 엔드포인트는 **키가 필요 없습니다.** 키가 필요한 엔드포인트를 쓸 때만 설정하세요.
`js/store.js` 가 지키는 약속입니다.

- 키는 **이 기기의 브라우저 `localStorage` 에만** 저장하며, 어떤 서버로도 보내지 않습니다.
- 전송이 필요할 때는 **URL이 아닌 HTTP 헤더**로만 보냅니다.
  URL 쿼리에 넣으면 브라우저 기록·중계 서버 로그·`Referer` 헤더에 평문으로 남습니다.
- 키는 콘솔에 출력하지 않고, **번호 복사·텍스트 저장에도 절대 포함하지 않습니다.**
- 설정값과 키는 저장소 키를 분리해 보관합니다. 설정을 내보내도 키가 섞여 나가지 않습니다.
- 화면에는 항상 마스킹해 표시하고(`sk••••••••34`), '보기'를 누를 때만 원문을 드러냅니다.
- 헤더 이름과 접두어(`Authorization` / `Bearer`)는 설정에서 바꿀 수 있습니다.

> **주의**: 브라우저 저장소는 암호화되지 않습니다. 공용 PC에서는 쓰고 나서 '삭제'를 누르세요.

이 항목들은 자동 테스트로 검증합니다 (`npm test` → `[7] API 키 취급`).

### 단일 파일 `lotto-standalone.html`

호스팅도, 인터넷도, 설치도 필요 없습니다. **파일 하나를 핸드폰에 복사해 브라우저로 열면 끝입니다.**

이렇게 만들려면 두 가지를 해결해야 했습니다.

1. `file://` 에서는 **ES 모듈 `import` 가 CORS 로 막힙니다.** 그래서 빌드할 때
   `import`/`export` 를 걷어내고 4개 모듈을 클래식 스크립트 하나로 합칩니다.
2. `file://` 에서는 **`fetch` 도 막힙니다.** 그래서 1241회차 데이터를 코드에 직접 박아넣고
   `loadDraws()` 의 fetch 호출을 그 상수로 치환합니다.

`npm run test:dist` 가 이 파일을 **fetch 를 아예 주지 않은 채** 실제로 구동해
데이터 로드·번호 생성·조합 확률·초기화까지 동작하는지 확인합니다.

> 단일 파일에도 외부 URL 이 딱 하나 남아 있습니다 — 설정의 기본 갱신 엔드포인트입니다.
> 페이지를 열 때 부르는 게 아니라 '최신 회차 가져오기' 를 눌렀을 때만 쓰이므로
> 오프라인 동작에는 영향이 없습니다. 검사가 이 사실을 계속 지킵니다.

**핸드폰에 넣는 법**: USB 로 연결해 복사하거나, 메일·카카오톡으로 자기 자신에게 보낸 뒤
받은 파일을 브라우저로 엽니다. 안드로이드는 크롬 메뉴에서 `홈 화면에 추가` 도 됩니다.

참고용 `twa-manifest.json` 을 `dist/android/` 에 넣어 뒀습니다.

iOS 는 APK 개념이 없고 앱스토어 배포에 Mac + Xcode + 개발자 계정(연 $99)이 필요합니다.

### 캐시 주의

캐시 전략은 **network-first** 입니다. 온라인이면 최신을 쓰고 실패하면 캐시로 되돌아갑니다.

> **앱 파일(HTML/CSS/JS)을 수정한 뒤에는 `sw.js` 의 `CACHE = 'lotto-v1'` 버전을 올리세요.**
> 데이터(`draws.json`)는 network-first라 저절로 갱신되지만, 설치된 앱 껍데기는
> 캐시 이름이 바뀌어야 확실히 교체됩니다.

## 데이터 자동 갱신

`.github/workflows/update-draws.yml` 이 매주 최신 회차를 자동으로 받아 커밋합니다.
푸시되면 GitHub Pages가 자동 재배포되고, 앱은 `sw.js`의 network-first 정책 덕에
사용자 쪽에서도 새 데이터를 받습니다.

| 항목 | 값 |
|---|---|
| 실행 시각 | 매주 **일요일 01:00 KST** (`cron: '0 16 * * 6'`, 토 16:00 UTC) |
| 근거 | 추첨이 토요일 20:45 KST이므로 약 4시간의 여유 |
| 수동 실행 | Actions 탭 → `당첨번호 자동 갱신` → Run workflow |

동작 순서와 안전장치:

1. 최신 회차 수집 (`tools/fetch_draws.py`) — 실패하면 거기서 중단, 커밋하지 않습니다.
2. **데이터 무결성 검증** — 회차 누락·중복·범위 이탈·정렬 오류를 확인합니다.
3. **엔진 회귀 검사** (`tools/selftest.mjs`) — 새 데이터로도 엔진이 정상인지 확인합니다.
4. `data/draws.json` 이 실제로 바뀐 경우에만 커밋·푸시합니다.

새 회차가 없으면 수집기가 파일을 아예 건드리지 않으므로 **빈 커밋이 생기지 않습니다.**

### Actions를 쓰지 않는다면 (Windows 작업 스케줄러)

```powershell
$action  = New-ScheduledTaskAction -Execute "python" `
           -Argument "tools\fetch_draws.py" -WorkingDirectory "C:\Users\kcseo\lotto-app"
$trigger = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Sunday -At 1am
Register-ScheduledTask -TaskName "로또 데이터 갱신" -Action $action -Trigger $trigger
```
